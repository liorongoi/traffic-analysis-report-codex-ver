# 07 — Hardware profiles and offline deployment

Target: Windows workstation, 16/48 GB RAM, RTX A4000 or other graphics, one active user. Development execution on this Mac does not establish Windows or GPU compatibility.

An on-demand local host report now reads CPU model/logical cores, OS-reported physical and available memory, GPU/driver details when an inventory utility is present, ONNX Runtime provider names, and free disk capacity. It does not load a vision model. Provider names are marked advertised only; GPU execution remains unverified until the selected model successfully runs on that provider. An on-demand 8 MiB write+fsync and immediate read probe measures the app-data volume; the read may be served from OS cache, so this is not a sustained-storage benchmark. The report proposes a conservative CPU memory profile from current capacity. The Windows implementation and target measurements still require native workstation validation. RAM profile and GPU choice are independent. Integrate bounded decoding/tiling/frame queues; avoid eager model loading and simultaneous inference/training memory contention. Proposed budgets reserve OS/application headroom and must be measured on both target classes; they are not performance guarantees.

## Packaging design

Create immutable, versioned prerequisite/runtime/model packs plus small application updates. Stage pinned wheels, native libraries, local models, codecs, timezone data/boundaries, fonts and scripts on an internet-connected build machine. Record software/weights/data licenses separately and create a content manifest. Include all actual required assets in copy-ready media. No package managers/model pulls/CDNs/telemetry during installed operation or installation.

Installation and normal operation must not need administrator privileges. Use %LOCALAPPDATA%, current-user shortcuts and private runtimes. Local folders and authorized UNC shares are required. Autostart and credential handling remain design/testing work. Do not install a system service/global runtime. The preview binds to loopback by default. Optional LAN mode requires a non-loopback `--host`, exact browser-facing `--public-host`, existing TLS certificate/key, and `TRAFFIC_ACCESS_CODE` of at least 16 characters (environment variable, never a CLI argument). It enables TLS 1.2+, checks Host and Origin, rate-limits failed access-code attempts, issues one active HttpOnly/Secure/SameSite=Strict session for 12 hours, and protects writes with a session token. Configure a browser-trusted certificate and a host firewall rule limited to authorized clients; do not expose the service to the public internet. Source implementation is present, but native Windows, trusted-certificate, firewall and two-computer acceptance remain required. Missing packs/unsupported GPU must fail clearly or use an explicitly selected CPU mode, never silently download/substitute a model.

Installation performs resumable content/native checks; normal launch reuses a receipt bound to exact content. App updates journal changes and preserve mission DB/evidence/checkpoints. Validate actual EXE contents and copied-file hashes independently, then verify native Windows offline installation/update/rollback on target hardware.

The current staging source rejects non-Windows/non-x64 Python executables, checks each installed package against the exact versions in `requirements-inference-windows.lock.txt`, requires offline tzdata, verifies both the vehicle and crop-only plate model packs, and includes both model packs, video/image worker entry points, web assets, and operator/deployment documentation in the payload manifest. Windows run `40275479409` completed the 234-test suite and staged the offline payload, confirming the pinned runtime, wheels, model packs and manifest work on the GitHub Windows runner. Inno Setup then failed because `dist/windows` did not exist when the compiler attempted to write the EXE. The workflow now creates that output directory before compiling; this fix awaits a fresh run. The install verifier checks all copied file hashes and runs CPU smoke inference for both models before writing a receipt; the normal launcher requires that receipt to match the manifest. Windows installer compilation, installation, uninstall, offline operation, update/rollback, and target hardware performance are still unverified.

Foundation budget function uses physical/available RAM conservatively but does not allocate memory or prove throughput. Actual native probes, packaging and GPU operation remain planned.
