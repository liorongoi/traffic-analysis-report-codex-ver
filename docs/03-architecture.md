# 03 — Architecture and data model

## Workstation topology

Authorized local/LAN browser → local web backend → mission service → durable per-mission queue → isolated worker processes. Backend owns databases, evidence storage and exports. A browser disconnect does not own worker lifetime. LAN binding is explicit and uses TLS 1.2+, exact Host/Origin checks, and a process-local token for writes; the user has directed that the app have no sign-in screen or account flow. No separate Windows Server, cloud, Docker or WSL is required.

Use spawn-compatible worker processes on Windows. Load only a selected adapter/model pack. Framework imports must be lazy. Missing weights/adapters produce an explicit unavailable state, never random detections. Model runtimes and immutable weights are separate from writable checkpoints.

## Per-mission storage

`<workspace>/missions/<UUID>/mission.sqlite3`, with private evidence, checkpoints and exports directories beside it. Source and output paths are never used as database names. A registry must not aggregate analytical results. Transactions and optimistic revisions protect edits, even with one operator using multiple browser tabs.

Foundation entities: mission configuration; runs and immutable configuration snapshots; versioned sources; run/source membership; append-only original predictions; append-only corrections with previous-revision linkage; review/reference eligibility; revisioned camera-view assignments; local scan windows; source-monitor checkpoints; and export snapshots. Inference snapshots include the mission configuration, source-run metadata, model configuration, schedule rules, view assignments and effective ROI. The video pipeline runs PyAV/FFmpeg in a spawned decoder process and sends one RGB frame at a time over a backpressured pipe to detection and tracking, avoiding co-loading PyAV/OpenCV FFmpeg dylibs. It enforces a maximum decoded pixel count, retains exact integer PTS/time base, reports frame progress, checks cancellation between frames, and closes active tracks at EOF. A policy-configured tracker carries same-recording identities through serialized checkpoints and marks ambiguous matches uncertain; thresholds have no defaults and must be explicit. Per-mission video sources are copied immutably with SHA-256, each run freezes source/origin/model/tracker configuration, checkpoints and closed-track event writes commit atomically, event IDs are run-scoped and idempotent, and event review revisions are append-only. Human event timing corrections snap to saved analyzed observations of the same track, preserve the original interval, and remain effective through later review actions; clip and table exports use the corrected interval while retaining original timing and correction provenance. A supervised child worker now runs the real local CPU vehicle proposal adapter, shares the existing single-worker slot with still-image inference, and exposes source registration, run start/status/cancel/resume, event listing and review APIs. Worker PID recovery marks orphaned active jobs failed and resumable without discarding checkpoints. Event UTC values derive from exact PTS/time-base plus explicit provenance-backed UTC origin; a missing origin is unresolved and must never be replaced by filesystem time or frame-index/FPS arithmetic. The browser supports video source registration, run configuration and lifecycle controls, paginated event review, integrity-checked byte-range playback, and event seeking. Operators can export H.264 MP4 event clips with explicit context; a durable ledger records source/run/event lineage and the output hash. Geometry-based camera-view grouping proposals are implemented, but held-out grouping acceptance remains open; native-target process recovery, native notifications, complete cross-adapter dataset management, YOLOX fine-tuning, and the full model-training lifecycle remain future work.

Every correction requires valid mission/run/source lineage and a real operator identity. It records before/after evidence, type, geometry/text/class when relevant, label role, review completeness and model/preprocessing provenance. Application roles must prevent direct arbitrary database manipulation. Bulk approvals are retained but are not eligible human references.

## Durable execution

Run transitions: queued → running → completed/failed/cancelled; running ↔ paused only where adapters support checkpointing. Completed/failed runs are immutable historical executions; retry creates a new run. Browser status is fetched from persisted events/progress. Each planned run must declare its input snapshot and algorithm version.

Current still-image General Traffic runs execute through a durable local worker using a staged CPU YOLOX-S model pack; model boxes and experimental night-light outputs remain unconfirmed proposals. Per-image progress, cancellation/resume, and worker-exit reconciliation are implemented. Video decoding, tracking, durable event review, bounded source-frame event previews with saved vehicle boxes, and supervised execution are implemented; browser playback/event seeking and audited H.264 event-clip export are implemented; representative media and native Windows validation remain outstanding. Plate processing localizes regions, saves crops, and provides a pinned CPU OCR suggestion for Latin and Arabic/Persian text. Chip approval is separate from append-only human text accept/correct/reject/unreadable decisions; OCR is not ground truth, and vehicle identity lookup is excluded. Target-country accuracy remains unvalidated. YOLOX training and controlled model promotion remain unimplemented. A separate mission-local light-correction candidate can be refit only from explicit eligible labels.


Continuous still-image monitoring uses backend-owned filesystem notifications to wake scans sooner when available. Periodic full reconciliation remains authoritative and visibly serves as fallback when notification setup fails or the source is unavailable. The watcher is dynamically reconfigured when mission monitoring settings change.
