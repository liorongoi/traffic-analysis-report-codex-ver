# 05 — Camera views, nighttime hypotheses and learning

Cameras are fixed at locations with multiple recurring views. Operators can create/rename groups, individually or explicitly batch-reassign images with revision history, inspect representatives, and snapshot view assignments into inference runs. A local grayscale/CLAHE + ORB retrieval + RANSAC geometry pass now proposes recurring groups, representatives and members; it never writes assignments. Operators inspect every suggested member and use the existing manual group/assignment controls to accept or change them. Local contrast normalization reduces sensitivity to brightness changes, but is not proof that illumination changes never split a physical view. Similarity scores are uncalibrated, the 1,200-image compute bound remains, and held-out camera grouping validation is outstanding. Operators can draw validated inclusion/exclusion polygons in normalized original-image coordinates on an assigned image. Region edits/deletes are append-only and each inference run records the active polygons and revisions; exclusions override included areas and filter detector/light proposals by box center. Inferred split/merge, view-change detection, and automated validity/invalidation review remain unimplemented. Background and ROI validity must be specific to view and condition. Large shifts/zoom changes require review.

## Nighttime pipeline proposal

Original image → exposure/quality assessment → native-coordinate ROI → vehicle/small-object branch + light-component branch + per-view persistent-background evidence → compatible evidence fusion → separate candidates and confirmed vehicles. Enhancement is derived input, not independent corroboration. Never assume every new bright pixel or pair is a vehicle. Model glare/reflections/wet-road effects and avoid absorbing stationary vehicles into background.

A vehicle can appear as one unresolved bright region, two nearby headlights, then a visible body. Save light-component hypotheses and grouping evidence separately from whole-vehicle predictions. Still counts remain independent. Only continuous video evidence can support a track through those transitions. A pair becoming visible must not double the vehicle/event count. Distance/type/color remain unknown without supporting evidence/calibration.

## Offline object search

The current still-image search uses a constrained local English/Hebrew grammar instead of a language model. It supports the saved detector's broad vehicle categories, exclusions, and explicit color/fine-subtype requests. Before execution the UI displays the typed interpretation and exact immutable inference run; that run already freezes local schedule, view assignment and ROI decisions. Execution requires a separate operator confirmation and searches only saved proposals or human annotations bound to that run. It executes no generated code and treats no model explanation as evidence. Current predictions do not encode color or pickup/SUV/van subtype, so such matches remain explicitly uncertain. The constrained grammar also accepts weekday and ISO date filters, explicit 24-hour local-time ranges, and named camera views used by the saved run. It applies date bounds inclusively, time ranges start-inclusive/end-exclusive, after/before bounds, and anchors overnight weekday/date filters to the window start day in the run’s IANA zone. Explicit phrases such as “from Sunday 17:00 through Monday 05:00” and “מיום ראשון 17:00 עד יום שני 05:00” map to one Sunday-anchored overnight window; invalid weekday spans are rejected. A query may combine up to four explicit time ranges with OR semantics; overnight windows are each anchored to their start weekday/date. Unique named ROI polygons are searchable against the exact saved geometry using phrases such as “in ROI Northbound lane”, “in the saved region named Northbound lane”, or “on Northbound lane”. Proximity terms such as “near” are rejected because the current geometry filter means inside the polygon. Arbitrary unnamed region interpretation, broad schedule phrasing, and broader target attributes remain future work.

## Correction lifecycle

Append every edit with source checksum/run/view/model/operator/time and revision. Preserve raw predictions. Latest approved correction defines a current decision, while prior revisions remain audit evidence. View reassignment and ROI edits are configuration changes, not object labels. Bulk approval is not human ground truth. Partial review does not label every unmarked pixel/object as negative. Plate-image workflow is limited to locating a plate region, saving its crop, and recording an operator approval or rejection. Never store or infer plate text, normalized plate values, or identity matches.

Training selection requires explicit human review, approved data roles and source retention. Keep mission boundaries; no automatic cross-mission pooling. No trigger threshold is approved. Each adapter must state real training/refit/calibration capabilities. Model candidates preserve base checkpoint/dataset IDs/settings/resources/metrics and failures. Compare with a held-out, camera/time-disjoint evaluation set and report regressions, including light-only and each country. No automatic promotion merely because training succeeded; retain rollback.

The current increment includes a local CPU YOLOX-S vehicle-proposal adapter and an experimental light-candidate/background path; see [real vehicle detection and review](10-vehicle-detection.md). These are not validated traffic counts, and no independent accuracy benchmark is available. The night-light head has a separate explicit-label refit path with saved evidence, candidate hashes, validation reporting and explicit per-run selection; choosing no head returns to the base context rules. Inventory distinguishes fully reviewed and partially corrected source images by evidence role; fitting still uses only explicit, confidence-qualified region labels and never treats unmarked content in a partial review as a negative. Each candidate's immutable evidence records per-region review status and role counts alongside the eligible dataset/version hash, downstream algorithm and preprocessing configuration, class schema, no-base-checkpoint rationale, and a bounded CPU single-worker profile, including training/validation region and source-image pixel limits. An explicit, one-time-per-unchanged-label-manifest action reports patch-level performance on held-out test labels; its fingerprint includes class labels and upgrades still recognize legacy fingerprints to prevent test-set reuse. When a different promoted head is active, the report compares candidate and current metrics on the same feature vectors without promoting either model. It also compares the candidate with saved contextual-light proposal subtypes on paired held-out regions that retain a linked production prediction ID, and reports coverage; this comparison does not rerun the full detector/background pipeline. YOLOX fine-tuning, numeric promotion criteria and complete training-data management across adapters remain unimplemented.

The UI and `/api/learning/capabilities` endpoint expose a structured declaration for each shipped algorithm: YOLOX-S, night-light context heuristics, the separate multinomial night-light head, per-view background references, crop-only plate localization, video association, camera-view proposals, and the offline search grammar. Each declaration states fine-tuning, full retraining, downstream-classifier training, background-model refitting, parameter calibration, available controls, and limitations. Only the separate light head supports downstream-classifier training; per-view context supports background-reference rebuilding. No row claims vehicle-detector fine-tuning or production calibration.
