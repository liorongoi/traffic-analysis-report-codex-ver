# 05 — Camera views, nighttime hypotheses and learning

Cameras are fixed at locations with multiple recurring views. Operators can create/rename groups, individually or explicitly batch-reassign images with revision history, inspect representatives, and snapshot view assignments into inference runs. A local grayscale/CLAHE + ORB retrieval + RANSAC geometry pass now proposes recurring groups, representatives and members; it never writes assignments. Operators inspect every suggested member and use the existing manual group/assignment controls to accept or change them. Local contrast normalization reduces sensitivity to brightness changes, but is not proof that illumination changes never split a physical view. Similarity scores are uncalibrated, the 1,200-image compute bound remains, and held-out camera grouping validation is outstanding. Operators can draw inclusion/exclusion polygons or request standalone SAM 3.1 text-prompted road masks in normalized original-image coordinates on an assigned image. A chosen suggestion remains a draft until the operator saves it as an analysis area or road surface. Analysis-area inclusion polygons mask pixels outside the selected area before YOLO and light proposal passes; exclusions and center-based filtering remain active. Region edits/deletes are append-only and each inference run records active polygons and revisions. Regions can be marked as analysis areas or road surfaces; road-surface polygons are reference geometry and do not filter detections. Vehicle boxes receive review-only on-road, near-road, off-road, or unknown labels based on bottom-center/intersection/proximity geometry. Road boundaries still require operator approval; SAM suggestions never decide a region role. Inferred split/merge, view-change detection, and automated validity/invalidation review remain unimplemented. Background and ROI validity must be specific to view and condition. Large shifts/zoom changes require review.

## Nighttime pipeline proposal

Original image → exposure/quality assessment → native-coordinate ROI → vehicle/small-object branch + light-component branch + per-view persistent-background evidence → compatible evidence fusion → separate candidates and confirmed vehicles. Enhancement is derived input, not independent corroboration. Never assume every new bright pixel or pair is a vehicle. Model glare/reflections/wet-road effects and avoid absorbing stationary vehicles into background.

A vehicle can appear as one unresolved bright region, two nearby headlights, then a visible body. Save light-component hypotheses and grouping evidence separately from whole-vehicle predictions. Still counts remain independent. Only continuous video evidence can support a track through those transitions. A pair becoming visible must not double the vehicle/event count. Distance/type/color remain unknown without supporting evidence/calibration.

## Offline object search

The current still-image search uses a constrained local English/Hebrew grammar instead of a language model. It supports the saved detector's broad vehicle categories, exclusions, and explicit color/fine-subtype requests. Before execution the UI displays the typed interpretation and exact immutable inference run; that run already freezes local schedule, view assignment and ROI decisions. Execution requires a separate operator confirmation and searches only saved proposals or human annotations bound to that run. It executes no generated code and treats no model explanation as evidence. Current predictions do not encode color or pickup/SUV/van subtype, so such matches remain explicitly uncertain. The constrained grammar also accepts weekday and ISO date filters, explicit 24-hour local-time ranges, and named camera views used by the saved run. It applies date bounds inclusively, time ranges start-inclusive/end-exclusive, after/before bounds, and anchors overnight weekday/date filters to the window start day in the run’s IANA zone. Explicit phrases such as “from Sunday 17:00 through Monday 05:00” and “מיום ראשון 17:00 עד יום שני 05:00” map to one Sunday-anchored overnight window; invalid weekday spans are rejected. A query may combine up to four explicit time ranges with OR semantics; overnight windows are each anchored to their start weekday/date. English “weekdays”/“weekends” and Hebrew weekday/weekend group phrases map to explicit local weekday sets. Unique named ROI polygons are searchable against the exact saved geometry using phrases such as “in ROI Northbound lane”, “in the saved region named Northbound lane”, or “on Northbound lane”. Proximity terms such as “near” are rejected because the current geometry filter means inside the polygon. Arbitrary unnamed region interpretation, broad schedule phrasing, and broader target attributes remain future work.

## Correction lifecycle

Append every edit with source checksum/run/view/model/operator/time and revision. Preserve raw predictions. Latest approved correction defines a current decision, while prior revisions remain audit evidence. View reassignment and ROI edits are configuration changes, not object labels. Bulk approval is not human ground truth. Partial review does not label every unmarked pixel/object as negative. The plate workflow stores the detector crop and original local OCR suggestion, then records separate append-only human acceptance, correction, rejection, or unreadable decisions. Preserve original Unicode text, leading zeros, and order alongside a separate normalized search key. Never perform vehicle-owner lookup or use external registries. OCR and target-country formats remain unvalidated until representative samples are reviewed.

Training selection requires explicit human review, approved data roles and source retention. Keep mission boundaries; no automatic cross-mission pooling. No trigger threshold is approved. Each adapter must state real training/refit/calibration capabilities. Model candidates preserve base checkpoint/dataset IDs/settings/resources/metrics and failures. Compare with a held-out, camera/time-disjoint evaluation set and report regressions, including light-only and each country. No automatic promotion merely because training succeeded; retain rollback.

The current increment includes a local YOLOX-S vehicle-proposal adapter (automatic DirectML with CPU fallback on Windows; CPU on macOS) and an experimental light-candidate/background path; see [real vehicle detection and review](10-vehicle-detection.md). These are not validated traffic counts, and no independent accuracy benchmark is available. The night-light head has a separate explicit-label refit path with saved evidence, candidate hashes, validation reporting and explicit per-run selection; choosing no head returns to the base context rules. Inventory distinguishes fully reviewed and partially corrected source images by evidence role; fitting still uses only explicit, confidence-qualified region labels and never treats unmarked content in a partial review as a negative. Fitting requires a single verified camera view; operator-assigned view IDs work with local camera-folder imports, while the Fintraffic fixture retains its filename-derived view key. Validation must use that same view, and saved candidate inference rejects inputs assigned to a different view. Each candidate's immutable evidence records per-region review status and role counts alongside the eligible dataset/version hash, downstream algorithm and preprocessing configuration, class schema, no-base-checkpoint rationale, and a bounded CPU single-worker profile, including training/validation region and source-image pixel limits. An explicit, one-time-per-unchanged-label-manifest action reports patch-level performance on held-out test labels; its fingerprint includes class labels and upgrades still recognize legacy fingerprints to prevent test-set reuse. When a different promoted head is active, the report compares candidate and current metrics on the same feature vectors without promoting either model. It also compares the candidate with saved contextual-light proposal subtypes on paired held-out regions that retain a linked production prediction ID, and reports coverage; this comparison does not rerun the full detector/background pipeline. The separate optional YOLOX-S fine-tuning CLI is implemented and consumes protected training/validation roles, but it runs outside the in-app learning worker; target-GPU execution and held-out detector evaluation remain unverified, while numerical promotion criteria and complete training-data management across adapters are still unimplemented.

The UI and `/api/learning/capabilities` endpoint expose a structured declaration for each shipped algorithm: YOLOX-S, night-light context heuristics, the separate multinomial night-light head, per-view background references, plate localization with local OCR suggestions and separate human text review, video association, camera-view proposals, and the offline search grammar. Each declaration states fine-tuning, full retraining, downstream-classifier training, background-model refitting, parameter calibration, available controls, and limitations. The separate light head supports downstream-classifier training; the YOLOX-S row now declares supported fine-tuning through the optional external CLI, protected-split export, and mission-local model-pack import/selection. Per-view context supports background-reference rebuilding. The declaration does not claim that training runs inside the app or that a candidate passed held-out or target validation; no row claims full retraining or production calibration.


## Reviewed image dataset export

The learning panel can package the latest still-image review snapshot as COCO JSON plus copied source images. It keeps training, validation, and test roles separate, includes complete reviews only, and includes only explicit human reviewed non-rejected boxes. Full reviewed images with no accepted human regions remain negative examples; partial reviews are excluded instead of assigning negatives to their unmarked areas. Model proposals, OCR suggestions, and bulk approvals are never labels. Export stops when identical source hashes or a known camera/hour group span multiple roles. Each package has a manifest with source hashes, review revisions, split counts, category schema, a deterministic evidence-version SHA-256, and the capture snapshot boundary. This is generic image dataset packaging; it does not fine-tune YOLOX or claim model quality.

## Optional offline vehicle training

The fine-tuning CLI uses only protected training and validation roles; the held-out test split is excluded. A separate stager packages a preprepared Windows CUDA/PyTorch runtime and YOLOX source without enlarging the single app installer. The transfer bundle carries a file-hash manifest and a target-side CUDA smoke command. It performs no downloads or sign-in. A real target-GPU training run and detector holdout evaluation remain unverified.
